## 2. Decisiones

| # | Decisión | Evidencia |
|---|---|---|
| D1 | **No se despliega en el servidor de la UFPS.** El backend y el frontend siguen en Render. Se mantiene la condición de una sola base con el Módulo de Matrícula. TP-139, TP-141, TP-153 y TP-155 se **reescriben** (no se borran ni se cierran) y conservan su alcance original al final de la descripción, por la trazabilidad de la auditoría | Comentarios en Jira de TP-139, TP-141, TP-153 y TP-155 |
| D2 | La base compartida es **la BD de producción del Módulo de Matrícula**, un addon MySQL en **Northflank** que administra su equipo (al redactar se escribió «Aiven»; Matrícula lo aclaró el mismo 16/11/2026). Sigue vigente la estrategia de TP-208 §5: tablas separadas con prefijo `tp_` e integración solo por API REST. **No** se leen tablas de Matrícula | `docs/BD_COMPARTIDA_MATRICULA.md` |
| D3 | Matrícula ejecuta los permisos y el DDL que se les entregan. Trámites carga sus datos con el usuario `tramites_app`. Como las tablas ya existirán, el backend arranca con `FLYWAY_BASELINE_VERSION=1` | PR #73 (`docs/entrega-matricula/`), ensayado en MySQL 8.0.44 con `sql_mode` ANSI |
| D4 | Railway quedó **fuera de servicio** al vencer la prueba gratuita, y producción está caída. Los datos eran de prueba y no había respaldo, así que se **arranca en limpio** en la BD compartida, sin migrar datos. Las cuentas iniciales se reconstruyen con las semillas de `data.sql` y los 6 estudiantes que quedaron en la copia de Matrícula. Las contraseñas son nuevas y el script de cuentas no va en el repositorio | `docs/CORTE_RAILWAY_A_AIVEN.md` §0 (PR #74), `docs/PLAN_RESPALDO.md` §4 |
| D5 | Se aprueba la migración **V3** (catálogos obligatorios con `INSERT IGNORE`). Cierra el pendiente de TP-208 §7.1 punto 6 | PR #75, probada en los dos escenarios de baseline |
| D6 | Se adoptan el CMR, el `.mailmap`, las métricas de configuración y el plan de respaldo como acciones correctivas de AUD-06 | PR backend #76 y frontend #51 |
| D7 | Se registra la observación **M3**: 0 de 17 PR fusionados desde el 03/11/2026 tienen aprobación formal (*Approve*) de alguien distinto del autor. Desde hoy el revisor marca *Approve* antes de fusionar. Activar la regla técnica en `develop` queda para la próxima reunión ordinaria | `docs/METRICAS_CONFIGURACION.md` |
| D8 | El ADD pasa a v3.1: BD compartida, sin despliegue UFPS, decisiones ADR-SC02-1 a 4, riesgos R9 y R10, diagrama y portada | Google Doc del ADD, PR #77, comentarios en TP-206 |
